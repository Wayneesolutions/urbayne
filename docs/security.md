# Security review and plan (P0 item 11)

Election data is a target: voter phone numbers, who supported whom, and who said "stop". This is what was reviewed, what was fixed, what is still open, how secrets are rotated, and what an outside penetration tester should cover.

**Not done: an external penetration test.** That needs a person or firm outside the team and cannot be done from code. Section 5 is the brief to give them.

### Accepted or open

- **Access tokens live 15 minutes and cannot be recalled** (logout and "sign out everywhere" end the refresh token at once). To cut everyone off immediately, replace `JWT_SECRET`.
- **Staff flag in the token** is trusted until the token expires (15 minutes) after a staff member is removed.
- **Phone encryption and hash keys cannot be rotated yet.** They are generated once and protected from deletion. Rotating needs a re-encryption job (not built). Treat them like the master keys: restrict who can read the secret.
- **The Vapi webhook is protected by a shared secret** (header compared in constant time), not by a network allow-list.
- **Inline styles are allowed** by the CSP (the pages use them); scripts are not.
- **The container runs the TypeScript sources with `tsx`**, so development tooling is in the image. A compiled build would be smaller; not urgent for security.
- **Redis and database passwords** are generated by Terraform and rotated by re-applying; there is no automatic rotation.
- Infrastructure code is **not validated or applied yet** (`infra/README.md`).

## 2. Controls in place

- Passwordless login by one-time code: 5 attempts per code, 3 codes per number per 10 minutes, per-IP limits (shared in Redis), codes stored only as keyed hashes, delivery failure burns the code.
- Phone numbers: AES-256-GCM at rest, keyed HMAC hash for lookup, masked in every API answer, never in logs or error reports.
- Tenant isolation: every query runs inside a transaction with the campaign id set, enforced by Postgres row-level security; the app connects as a role that RLS applies to.
- Guardrails: no caste or religion fields (unknown fields rejected), no WhatsApp automation (CI check), no bought or scraped lists without proof, one client per race.
- Audit log is append-only for the app role. Evidence seals and deletion records cannot be edited by the app.
- Personal data retention and erasure: see README ("Privacy").
- Uploads: none yet (receipt photos arrive in Phase 4 and need virus scanning, type checks and region-bound storage).

## 3. Secret rotation

| Secret | How to rotate | Effect |
| --- | --- | --- |
| `JWT_SECRET` / `JWT_REFRESH_SECRET` | Move the old value to `JWT_SECRET_PREVIOUS` / `JWT_REFRESH_SECRET_PREVIOUS`, set the new value, deploy. After 15 minutes (access) or 30 days (refresh) remove the `_PREVIOUS` value. To cut everyone off now, do not keep the previous value | Nobody is logged out during a planned rotation |
| `EVIDENCE_SIGNING_KEY` | Same pattern with `EVIDENCE_SIGNING_KEY_PREVIOUS`, so old PDFs still verify | Old seals keep verifying |
| Database owner / app passwords | Change the `random_password` resources (taint), apply, run the migrate task (it sets the app role password), restart services | Short restart |
| Redis auth token | Taint the `random_password`, apply, redeploy | Sessions and queued jobs are lost: do it in a quiet period |
| Vapi key, Twilio token, MSG91 key, Sentry DSN | Create the new key at the provider, update `provider_secrets`, apply, redeploy, then revoke the old key | None |
| `VAPI_WEBHOOK_SECRET` | Change the value; because the secret is sent per call, only calls in progress during the redeploy report with the old secret | A few reports may be rejected (cost is recovered by the lookup job) |
| `PHONE_ENC_KEY` / `PHONE_HASH_KEY` | **Not possible yet** (see above) | |

A schedule that is reasonable for launch: JWT and evidence keys every 6 months, provider keys every 12 months or when anyone with access leaves, and all of them immediately after any suspected leak.

## 4. Support access policy

Staff can read a campaign they are not a member of only with a stated reason (ticket number and why), only with GET requests, and every request is written to that campaign's audit log, which the campaign owner can see. Staff never see unmasked phone numbers (no API returns them). Changes are made by the campaign's own owner.

## 5. Brief for an external penetration test

**Targets**: the staging deployment of one edition (API, dashboard `/admin`, worker app `/w`, voter page `/v/:slug`, webhook endpoint `/webhooks/vapi`).
**Accounts to provide**: two campaigns with an owner each, one manager, one field worker; one staff account. Seeded demo campaigns are fine; no real voter data.
**Please try**: login and one-time-code abuse (brute force, enumeration, rate limit bypass, session fixation), token handling, cross-campaign access in every module (read and write), role escalation (worker to manager to owner), staff access rules, injection (SQL, JSON, headers, CSV export formulas), the public voter page and assistant (abuse, prompt injection, data leakage), webhook forgery, evidence seal forgery, denial of service on queues, secrets exposure (error messages, logs, headers), TLS configuration, and the cloud setup (security groups, IAM, secrets, public exposure).
**Out of scope**: provider platforms themselves (Vapi, Twilio, MSG91, AWS), social engineering, physical attacks, volumetric DDoS.
**Before the test**: run `pnpm audit`, `pnpm test`, and a Terraform plan review; fix everything above that is marked open and cheap to fix.
**After**: every finding gets a row in section 1 with a status, and a retest.

## 6. If something goes wrong

1. **Detect**: the alarms in `infra/` (error rate, failed jobs, 5xx) and Sentry, plus the audit log.
2. **Contain**: replace `JWT_SECRET` and `JWT_REFRESH_SECRET` (no `_PREVIOUS`) to log everyone out; rotate the provider keys involved; use `POST /api/auth/logout-all` for one user.
3. **Assess**: the audit log and request logs (request ids) show what was read and by whom. Phone numbers are encrypted, so a database copy alone does not expose them without `PHONE_ENC_KEY`.
4. **Notify**: breach notification duties (India's DPDP Act and rules, Canada's PIPEDA and provincial law, and the campaign's own contracts) have deadlines and content requirements that **counsel must confirm**; this document does not state them.
5. **Learn**: write down what happened, fix it, add a test.
